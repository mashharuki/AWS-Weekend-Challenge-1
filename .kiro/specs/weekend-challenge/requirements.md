# 要件定義書

## はじめに

本仕様は、AWS Community Builder の活動を支援するため、記事やアプリのアイデアを毎日自律的に収集・吟味し、英語のブログ形式 Markdown として届ける常時稼働のクリエイティブエージェントを定義する。最小限の機能で Weekend Creative Agent Challenge のアプリケーション要件と提出資料要件を満たすことを目標とする。

## 境界コンテキスト

- **対象範囲**: 自律的な定期生成、英語 Markdown の保存・閲覧、生成の証跡、AWS への再現可能な配備、提出用ドキュメント。
- **対象外**: ユーザー認証、共同編集、個別ユーザー向けの配信設定、生成コンテンツの手動編集機能。
- **隣接する期待**: 実装は既存の UI・API・インフラのアプリ境界を維持し、公開前に利用者が生成結果と提出資料を確認できる。

## 要件

### Requirement 1: 自律的な定期コンテンツ生成

**Objective:** As an AWS Community Builder, I want 操作しなくても毎日新しいアイデアが生成されること, so that 継続的に発信の着想を得られる。

#### Acceptance Criteria

1. When あらかじめ定めた実行時刻になると、システムは利用者による手動開始なしにコンテンツ生成を開始しなければならない。
2. When 定期実行が開始されると、システムは生成を一意に識別できる実行記録を作成しなければならない。
3. If 同一の定期実行が重複して通知された場合、システムは同じ実行記録に対して重複した公開用コンテンツを作成してはならない。
4. The システム shall 利用者の手動開始に依存せず、少なくとも日次で新しいコンテンツを生成できること。

### Requirement 2: 情報の収集・評価・創作的な整形

**Objective:** As an AWS Community Builder, I want 関連性のある情報から整理済みのアイデアを得ること, so that 調査と下書き作成の時間を減らせる。

#### Acceptance Criteria

1. When コンテンツ生成が開始されると、システムは AWS Community Builder の活動に関連する記事またはアプリの着想となる情報を収集しなければならない。
2. When 複数の情報候補を収集した場合、システムは関連性と新しさを考慮して生成に用いる候補を選定しなければならない。
3. When 選定が完了すると、システムは選定情報を基に、実行可能な記事またはアプリのアイデアを含む創作的なコンテンツを生成しなければならない。
4. If 十分な情報を取得できない場合、システムは不完全な結果を公開せず、実行失敗として記録しなければならない。

### Requirement 3: 英語 Markdown コンテンツ

**Objective:** As an English-speaking content creator, I want 生成結果を再利用しやすい記事形式で受け取ること, so that 発信のたたき台としてすぐに利用できる。

#### Acceptance Criteria

1. When コンテンツ生成が成功すると、システムは結果を英語で作成しなければならない。
2. The システム shall 見出し、本文、および少なくとも一つの具体的なアイデアを含む有効な Markdown 形式で結果を提供すること。
3. When 生成結果を保存すると、システムは生成日時、タイトル、本文、および生成状態を結果と関連付けなければならない。
4. If 生成結果が空、または必須の内容を欠く場合、システムはその結果を公開可能として扱ってはならない。

### Requirement 4: 生成済みコンテンツの閲覧

**Objective:** As an AWS Community Builder, I want 生成済みのアイデアをブラウザで確認すること, so that 最新の成果物を手早く発信に活用できる。

#### Acceptance Criteria

1. When 利用者がアプリケーションを開くと、システムは最新の公開可能な生成結果を表示しなければならない。
2. When 生成済みコンテンツを表示すると、システムは Markdown の見出し、段落、リスト、リンクを読みやすい形式で表示しなければならない。
3. When 複数の公開可能な結果が存在すると、システムは各結果のタイトルと生成日時を識別可能な形で表示しなければならない。
4. If 公開可能な結果がまだ存在しない場合、システムは生成待ちであることを利用者に明示しなければならない。

### Requirement 5: 実行状態と自律生成の証跡

**Objective:** As a challenge submitter, I want 自律実行と生成結果を確認できること, so that アプリケーション要件への適合を証明できる。

#### Acceptance Criteria

1. When 各生成実行が完了したとき、システムは成功または失敗の状態と完了時刻を記録しなければならない。
2. When 生成が成功したとき、システムは実行記録から対応する生成コンテンツを追跡可能にしなければならない。
3. If 生成処理のいずれかの段階で失敗した場合、システムは失敗した段階を識別できる情報を記録しなければならない。
4. The システム shall 自律実行により生成されたコンテンツの存在を、手動実行の結果と区別して確認できること。

### Requirement 6: 安全なデータ取扱い

**Objective:** As a project owner, I want 機密情報と生成データを適切に扱うこと, so that 公開アプリケーションを安全に運用できる。

#### Acceptance Criteria

1. The システム shall 認証情報、秘密値、またはアクセスキーを公開コンテンツ、クライアントへ返すデータ、ソース管理対象の設定に含めないこと。
2. When 外部サービスへの認証情報が必要な場合、システムは実行時にのみ認可された手段で取得しなければならない。
3. When 公開用データを返すと、システムは利用者の認証情報または内部運用情報を含めてはならない。
4. If 不正な形式または未検証のコンテンツを受信した場合、システムは安全に拒否または無害化してから保存・表示しなければならない。

### Requirement 7: 再現可能な AWS 配備と後片付け

**Objective:** As a project owner, I want 必要なクラウド資源を一括管理すること, so that アプリケーションを安全かつ再現可能に公開・削除できる。

#### Acceptance Criteria

1. When プロジェクトの配備操作を実行すると、システムはアプリケーションの実行、定期生成、データ保存、公開、および運用に必要なすべての AWS 資源を作成しなければならない。
2. When 配備が完了すると、システムは少なくとも一つの AWS サービス上で利用可能でなければならない。
3. When プロジェクトの削除操作を実行すると、システムは本アプリケーションのために作成した秘密情報およびログを含む管理対象資源を削除しなければならない。
4. The システム shall 資源の識別子とサービスごとの設定をアプリケーションの振る舞いから分離して管理できること。

### Requirement 8: 運用可能性と最小品質

**Objective:** As a project owner, I want 問題を把握して品質を確認できること, so that 限られた開発期間でも信頼できる成果物を提出できる。

#### Acceptance Criteria

1. When システムでエラーが発生した場合、システムは原因調査に必要な時刻、実行識別子、および失敗内容を記録しなければならない。
2. When コードまたはインフラを変更すると、システムはフォーマット、静的解析、および該当する自動テストを実行可能でなければならない。
3. When インフラ構成を変更すると、システムは意図したクラウド資源が定義されていることを自動テストで検証可能でなければならない。
4. The システム shall 最小構成で動作し、要件に不要な利用者向け機能を必須としないこと。

### Requirement 9: プロジェクト README とアーキテクチャ資料

**Objective:** As a repository visitor, I want アプリケーションの目的と操作方法を理解すること, so that 自分の環境で評価・再現できる。

#### Acceptance Criteria

1. The プロジェクト shall アプリケーションの目的、自律的な生成の流れ、および主要な利用者価値を説明する README を提供すること。
2. The プロジェクト shall AWS のサービス構成とデータの流れを表す AWS アイコン使用の draw.io アーキテクチャ図を提供すること。
3. The プロジェクト shall 前提条件、セットアップ、ビルド、配備、利用、削除の手順を README に提供すること。
4. When 利用者が README の手順に従うと、システムは追加の非公開手順なしにアプリケーションを配備および削除できなければならない。

### Requirement 10: Weekend Creative Agent Challenge 提出記事

**Objective:** As a challenge submitter, I want 完成した提出用記事を用意すること, so that アプリケーションの価値と要件適合を明確に説明できる。

#### Acceptance Criteria

1. The プロジェクト shall AWS Builder Center 投稿用の英語 Markdown 記事を提供すること。
2. The 記事 shall 500 語以上であり、タイトルに `Weekend Creative Agent Challenge:` とプロジェクト名を含めること。
3. The 記事 shall `agents` タグ、ビジョンと機能、構築過程、使用した AWS サービスとアーキテクチャ概要、学び、公開可能なアプリまたはリポジトリへのリンクを含めること。
4. When 提出前に記事を確認すると、システムは自律的またはスケジュール実行で生成された出力の証跡を記事またはリンク先で確認可能にしなければならない。
